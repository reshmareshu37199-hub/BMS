# Assumptions — BMS-FW-ASG-01

The assignment explicitly allows reasonable assumptions where the specification is unclear.
Every assumption below is deliberate, is reflected in the code, and is listed with its
rationale and impact so it can be challenged during the review.

Format: **ID — assumption.** *Why.* *Impact.*

---

## A. Platform and build

**A1 — Target class.** The timing budget assumes a 32-bit Arm Cortex-M4 class MCU at 64 MHz,
with no FPU use in hot paths. *The assignment only requires PC-host execution; a concrete
target is not named.* *Impact:* all WCET numbers in `docs/DESIGN.md` are estimates. The host
build uses x86-64, so its stack measurements are conservative upper bounds for a 32-bit
target.

**A2 — SPI clock.** SPI runs at 1 MHz and a 3–5 byte transfer costs 30–50 µs including
driver overhead. *Used only for the CPU-load estimate.* *Impact:* halving the SPI clock would
roughly double the 1 ms task cost but still leave large margin.

**A3 — Tick source.** A 1 ms SysTick increments a volatile millisecond counter; tasks run in
main context. No application logic executes in the tick ISR. *This is the standard
cooperative pattern and keeps shared-state analysis simple.* *Impact:* the scheduler's
granularity is 1 ms; tasks cannot preempt one another.

**A4 — Toolchain.** GCC 16.2.0, CMake 4.4.4, Ninja, C11, `-Wall -Wextra -Werror` plus the
extra warnings in `CMakeLists.txt`. *Matches the environment used to produce the evidence.*
*Impact:* MSVC is supported by the CMake file but was not used for the reported results.

**A5 — No Git/CI in the environment.** Git, lcov, gcovr, gnuplot, pandoc, clang-tidy and
Python were not installed. *The .git folder and a hosted CI run cannot be produced here.*
*Impact:* coverage is reported with `gcov` directly and plots are generated by a small C
tool; the commands are documented so the same evidence can be reproduced anywhere.

## B. AFE and measurement

**B1 — Frame format.** SPI frame: `[ADDR|R/W] [LEN] [DATA0..DATAn] [CRC8]`; bit 7 of the
address byte is 1 for write; CRC-8 poly 0x07, init 0x00, no reflection, no final XOR. A read
response is `[DATA…][CRC8]` with the CRC over the data bytes only. *Taken directly from the
assignment.* *Impact:* the simulator (`afe_sim.c`) implements exactly this contract.

**B2 — Device ID.** Register 0x00 returns 0x5A. Three failed read attempts latch an AFE
fault and keep the system out of service. *From the assignment.* *Impact:* an absent or
miswired AFE is detected at start-up.

**B3 — Conversion timing.** Writing 0x01 to ADC_CTRL starts a 2 ms conversion; the driver
polls STATUS once per 1 ms tick and reads one register pair per tick. *The assignment
requires non-blocking acquisition and does not mandate a read strategy.* *Impact:* a full
16-cell + 5-temperature cycle completes in ≈ 22 ms, well inside the 100 ms control cycle.

**B4 — Cell LSB.** Cell registers are 16-bit big-endian with 100 µV per LSB. *From the
assignment.* *Impact:* `cell_mv = raw / 10` (integer, truncating). A raw value of 36500
corresponds to 3650 mV.

**B5 — NTC conversion.** The 12-bit raw value is the divider output of a 10 kΩ pull-up to
3.3 V with Beta 25/85 = 3435, and is converted with a lookup table plus linear interpolation
to 0.1 °C. *The assignment permits Beta or a table and asks for the trade-off; the table avoids
`log`/`exp` and floating point in the 100 ms path.* *Impact:* accuracy is limited by the table
resolution (documented as adequate for protection, not metrology); a target calibration
would replace the table constants only.

**B6 — Temperature channels.** AFE TEMP1–4 are cell sensors; TEMP5 is reserved/board-related.
The application uses the maximum of TEMP1–4 for cell protection and balancing, duplicates
TEMP1 into the protection array's fifth slot to keep the scan simple, and reads the board NTC
from the HAL. *The assignment says 4 cell NTCs plus 1 board NTC but the AFE exposes 5
channels.* *Impact:* TEMP5 has no effect on protection; the board temperature is an
independent HAL input. This is the cleanest mapping without inventing a hardware topology.

**B7 — Cell-sum plausibility.** The sum of the 16 cell voltages must be within ±1000 mV of
the pack voltage, otherwise `CELL_SUM_MISMATCH` is raised. *From the assignment.* *Impact:* the
check is only meaningful when the AFE snapshot is valid; invalid snapshots do not generate a
sum fault.

**B8 — Pack and bus voltage.** `Hal_PackVoltageMv()` is the pack-side measurement and
`Hal_BusVoltageMv()` is the inverter/charger-side link voltage used for precharge. *The
assignment distinguishes pack and bus in the precharge description.* *Impact:* a bus reading
of 0 means the link is discharged; the simulator uses 0 to mean "tied to the pack" so
precharge completes immediately in scenarios that are not about precharge.

**B9 — Current sign.** Positive current means charge, negative means discharge, unit mA.
*From the assignment.* *Impact:* the SOC, protection and balancing signs all follow this
convention.

## C. Contacts, state machine and VCU

**C1 — Contactor model.** Each contactor is a boolean "closed" output; the precharge relay is
a third independent output. There is no separate feedback in the simulated HAL. *The
assignment describes two contactors plus a precharge relay.* *Impact:* the state machine
commands the sequence but cannot detect a welded contactor; that would need feedback inputs
on a real board.

**C2 — Precharge thresholds.** Precharge is complete when `bus ≥ 0.95 × pack`, the timeout is
2 s, and a 20 ms settle/overlap is used before and after the transition. *From the assignment
for the 95 %/2 s values; the 20 ms settle is an engineering choice to debounce the voltage
comparison and to guarantee overlap when closing the positive contactor.* *Impact:* the
precharge phase adds ≈ 40 ms plus the actual link charging time.

**C3 — INIT hold.** INIT lasts at least 200 ms after the first valid AFE snapshot. *Not
specified; gives the AFE a second conversion and lets the pack measurement settle.*
*Impact:* a 200 ms delay at start-up only.

**C4 — VCU timeout.** A missing/invalid VCU command for 300 ms is a timeout. The state
machine leaves DRIVE/CHARGE for STANDBY and opens the contactors after an additional 1 s.
The timeout is reported as a DTC but is **excluded** from the "any fault active" aggregation
used for FAULT entry. *The assignment says "go to STANDBY, open contactors after 1 s"; it
does not say FAULT.* *Impact:* a lost VCU is treated as a communication loss, not a hardware
fault; the DTC is still visible through UDS.

**C5 — VCU command semantics.** `ContactorReq` values 2 and 3 are invalid and are treated as
"not a close request". The close request must be accompanied by a valid CRC and a valid alive
counter. `FaultClearReq` is rising-edge sensitive. `SleepReq` is level sensitive. *From the
assignment and standard practice; edge detection prevents a stuck clear request from
continuously resetting latched DTCs.* *Impact:* a held clear request clears once, then waits
for a new edge.

**C6 — Charger presence.** `Hal_ChargerPresent()` decides whether a successful precharge
ends in CHARGE or DRIVE. *The assignment names both states but does not define a charger
signal; the BOM and scenario need one.* *Impact:* on a vehicle without a charger-detect line
this would be derived from current direction or a VCU bit.

**C7 — Fault hold policy.** Contactors are held closed for 1 s after entering FAULT unless the
fault requests an immediate open (over-current, hard OV/UV, precharge failure). *The
assignment explicitly asks for this "reduce current first" behaviour.* *Impact:* a fault that
clears within 1 s still opens and returns to STANDBY after the hold; the 1 s is not shortened.

**C8 — Hard thresholds.** OV opens immediately above 3750 mV and UV opens immediately at or
below 2300 mV, independent of the 1 s debounce and of the latched state. *From the
assignment's reaction column.* *Impact:* a fast transient can trip the immediate path even
while the normal DTC is still pending; both are reported.

**C9 — Precharge failure representation.** The state machine emits a one-cycle
`precharge_failed` pulse which the application feeds to protection as a fault input; the
protection layer latches `FAULT_PRECHARGE`. *This keeps the state machine free of DTC
knowledge and lets the latched fault be cleared through the normal path.* *Impact:* the pulse
must be consumed on the next 10 ms cycle, which the application does.

**C10 — SLEEP.** SLEEP is a contactor-open low-power state; it wakes when the sleep request
is removed and the VCU is valid. There is no separate low-power hardware entry in the PC
simulation. *The assignment lists SLEEP but does not define wake-up.* *Impact:* on target the
same transition would also disable transceivers and enter the MCU low-power mode.

## D. Balancing

**D1 — "Adjacent" means physically neighbouring cells n and n+1 in the 16-cell stack.**
*From the assignment.* *Impact:* the rule is implemented as `mask & (mask << 1)`; no
distinction is made between AFE channels and physical wiring.

**D2 — Start/stop semantics at the boundary.** Balancing starts when
`Vcell − Vmin > BAL_START_MV` (strictly greater) and continues while
`Vcell − Vmin ≥ BAL_STOP_MV`. *The assignment uses ">" for start and "<" for stop, leaving
the exact equality case open.* *Impact:* the default 15/5 mV band is 10 mV wide; equality
behaves as "continue bleeding" to avoid chatter.

**D3 — Vmin gate.** Balancing is allowed only when `Vmax ≥ BAL_VMIN_MV = 3400 mV`. *From the
assignment.* *Impact:* no balancing in the flat LFP region, where voltage differences are not
a reliable SOC proxy.

**D4 — Fairness band.** A cell that was dropped last cycle is promoted to the front of the
candidate list only if it is within 20 mV of `Vmax`. *The assignment asks how starvation is
prevented but does not prescribe a mechanism.* *Impact:* a genuinely much-higher cell still
wins; the priority only breaks ties among near-equal cells. The band is calibratable.

**D5 — Timeout.** Continuous balancing is limited to 8 h of accumulated active time; a charge
cycle is detected as current > 500 mA for one 100 ms cycle and clears the warning. *From the
assignment; the 500 mA threshold is an engineering choice to reject sensor noise.*
*Impact:* the timeout is a warning and a balancing inhibit, not a DTC.

**D6 — Temperature source.** "Cell temperature" is the maximum of the four cell NTCs; "board
temperature" is the separate HAL board NTC. Limits are 50.0 °C / 70.0 °C with a 5 °C resume
hysteresis. *From the assignment.* *Impact:* one hot cell inhibits all balancing, which is the
safe choice for a passive board.

**D7 — Discharge inhibit.** Balancing is inhibited when pack current is below −2 A. *From the
assignment.* *Impact:* a small parasitic load does not inhibit balancing; a real discharge
does.

**D8 — Measurement pause.** All bleed switches are forced off before each AFE conversion and
the new mask is applied only after a snapshot is published. *From the assignment.* *Impact:*
balancing duty cycle is reduced by the ≈ 22 ms acquisition window per 100 ms cycle
(≈ 78 % maximum duty), which is accounted for in the thermal design assumptions.

**D9 — Maximum cells.** At most 8 cells bleed at once (board thermal limit). *From the
assignment.* *Impact:* with 16 cells and no adjacent pairs the theoretical maximum is 8, so
the default limit is also the adjacency limit.

## E. Protection and DTCs

**E1 — DTC numbering.** The firmware uses 3-byte ISO 14229 DTCs in the manufacturer-specific
range: `0x000A01` … `0x000A0B`, one per fault in `FaultId` order. *The assignment requires
DTCs but does not assign numbers.* *Impact:* the numbers are stable and documented in
`docs/DESIGN.md` §6.1; a production project would replace them with the OEM's allocation.

**E2 — DTC status bits.** `testFailed` (0x01), `testFailedThisCycle` (0x02), `pending` (0x04),
`confirmed` (0x08), `testFailedSinceClear` (0x20) and `warning` (0x80) are used; the
availability mask returned to the tester is 0xFF. *ISO 14229-1 semantics, simplified to the
subset the assignment reports.* *Impact:* 0x19 0x02 returns records whose status matches the
requested mask.

**E3 — Latched clear.** A latched fault clears only when the release condition is true **and**
a clear request (UDS 0x14 or the VCU bit) arrives. A clear request while the condition is
still present is ignored. *From the assignment.* *Impact:* the DTC status becomes
"testNotCompletedSinceClear" after a successful clear rather than disappearing from the
server's memory; the active fault reaction stops.

**E4 — "While charging" and "while discharging".** Charging is `current > +500 mA`;
discharging is `current < −500 mA`. The 500 mA dead band prevents temperature faults from
chattering around zero current. *The assignment says "while charging" without a threshold.*
*Impact:* a charge over-temperature fault can be released by simply stopping charge, which is
the intended reaction (CCL = 0).

**E5 — Over-current debounce.** Discharge OC uses 500 ms, charge OC uses 1 s, as specified.
The immediate-open path is independent of these timers. *From the assignment.* *Impact:* the
fault is latched even if the current returns to zero before the debounce expires, which is
consistent with "latched".

**E6 — AFE communication fault.** Three consecutive failed acquisition cycles latch the
fault. A single successful cycle clears the failure counter but not the latch. Internal AFE
fault and open-wire status are folded into the same reaction (open, latched) without separate
DTC IDs. *The assignment only defines AFE_COMM_FAULT; adding IDs would exceed the required
DTC set.* *Impact:* the exact AFE failure cause is visible in the snapshot flags
(`internal_fault`, `open_wire`) but not as a distinct DTC.

**E7 — Cell-sum mismatch.** This is not latched; it clears when the sum returns within
tolerance and limits CCL/DCL to 0 while active. *The assignment does not mark it latched.*
*Impact:* a temporary measurement glitch recovers automatically.

**E8 — CCL/DCL tables.** The piecewise-linear tables in `docs/DESIGN.md` §9 are engineering
choices. CCL is 0 below 0 °C and above 55 °C; DCL is 0 below −20 °C and above 60 °C; voltage
limits taper from 3550→3650 mV (charge) and 2500→3000 mV (discharge). *The assignment asks
for "reasonable tables" and documentation.* *Impact:* the values are calibratable constants;
the ramp is 100 mA/ms = 10 A per 100 ms.

**E9 — Limits at boot.** CCL and DCL start at 0 and ramp up, so the first CAN frames cannot
command a step. *Safety default; not specified.* *Impact:* the vehicle sees a short ramp at
start-up.

**E10 — Fault bits.** CAN 0x354 `FaultBits` bit *n* corresponds to `FaultId` *n*; warnings use
a separate 16-bit mask. *The assignment leaves the mapping open.* *Impact:* the mapping is
stable and documented in `protection.h` and the DBC.

## F. CAN and UDS

**F1 — CAN framing.** 500 kbit/s, classic CAN, 11-bit IDs, 8-byte frames, Intel byte order.
*From the assignment.* *Impact:* no CAN-FD, no extended IDs, no remote frames.

**F2 — CRC and alive.** Messages with CRC use CRC-8 SAE J1850 over bytes 0–6 with byte 7 as
the CRC; the alive counter is 4 bits, wraps 15→0 and increments per transmission. 0x352,
0x353 and 0x354 have no CRC, as specified. *From the assignment.* *Impact:* a receiver can
detect corruption and stale data on the messages that need it.

**F3 — VCU command validation.** The receiver rejects a frame with wrong DLC, wrong CRC, an
unchanged alive counter, or an alive jump greater than 2 (modulo 16). Each error type is
counted; three consecutive invalid frames are treated as a timeout. *From the assignment.*
*Impact:* a single lost frame does not trip the timeout, but a stuck or spoofed counter does.

**F4 — CAN Tx overflow.** The software queue holds 8 frames and sends at most 4 per 1 ms
poll. If the queue is full the newest frame is dropped and counted. Periodic frames are
retransmitted on the next cycle. *The assignment asks how a full mailbox is handled.*
*Impact:* a burst cannot block the 100 ms task; the drop is observable in `CanDrvStats_t`.

**F5 — Signal saturation.** Physical values are saturated to the signal's representable range
before scaling, and the conversion uses a 64-bit intermediate. *From the assignment.*
*Impact:* an out-of-range value is clamped, never wrapped.

**F6 — DBC multiplexing.** 0x353 uses `MuxIdx` and three 16-bit cell signals per frame. The
DBC duplicates the three signals for mux values 0–5 so generic DBC tools decode every frame;
all muxes share the same byte layout. *Classic DBC has one multiplex value per signal, and
duplicating is the portable way to express "same layout for six muxes".* *Impact:* the DBC is
longer but unambiguous; `BalBits` is shared by all muxes.

**F7 — UDS sessions.** Default and extended sessions; extended times out after 5 s without a
request (S3). 0x2E is accepted only in extended. 0x3E 0x80 suppresses the positive response.
*From the assignment.* *Impact:* an unknown session or a write in default returns
NRC 0x7F / 0x22 as appropriate.

**F8 — DID formats.** 0xF189 is an ASCII software-version string. 0x0101 returns pack voltage
(mV, 2 bytes) and current (mA, 4 bytes signed). 0x0100 returns 16 × 2-byte cell voltages (32
bytes) and therefore requires ISO-TP multi-frame. 0x0200/0x0201 are 2-byte mV values.
*The assignment specifies the DIDs but not every byte layout; these layouts are documented in
`uds.c` and covered by tests.* *Impact:* the tester must use the documented layout; changing
it is a one-line response builder plus a test.

**F9 — UDS 0x14.** Only group `0xFFFFFF` is accepted; other groups return NRC 0x31. *From the
assignment.* *Impact:* group-specific clearing is not implemented.

**F10 — ISO-TP.** Classic 7-byte payload (8-byte CAN frame, first byte is the PCI), block
size and STmin are honoured on transmit, and the transmitter waits for a Flow Control between
blocks. In the PC simulator and in the multi-frame tests the tester injects the FC frame.
*The BMS is the responder; a real tester sends the FC.* *Impact:* a tester that never sends
FC will see the response abort after the FC timeout, which is correct behaviour.

**F11 — Response pending.** 0x78 is not used; every implemented service answers within the
control-cycle budget. *Not required by the assignment.* *Impact:* a future slow service
(e.g. flash erase) must add 0x78 handling.

## G. SOC (bonus B1)

**G1 — Battery constants.** Capacity 100 Ah, coulombic efficiency 990 ‰, initial SOC 500 ‰
when NVM has no valid record. *From the assignment's 100 Ah pack; the efficiency and initial
value are engineering choices.* *Impact:* a full pack takes ≈ 100 Ah of charge to go 0→100 %;
the 1 % loss models LFP coulombic efficiency.

**G2 — Offset learning.** The current offset is learned by averaging while |I| < 0.5 A for
30 s. *From the assignment's rest condition.* *Impact:* a persistent sensor bias is removed
at rest; a biased sensor under load is not corrected until the next rest.

**G3 — OCV correction.** Correction starts after 1 h at rest (`|I| < 0.5 A`) and is applied
with a 5 % weight between 3.28 V and 3.34 V and 25 % outside that band. *The assignment asks
how the correction is limited in the flat region; these weights are the answer.* *Impact:*
SOC converges slowly but avoids large jumps caused by a flat OCV curve.

**G4 — OCV table.** The supplied table (0/10/20/30/50/70/90/95/100 % → 2800/3200/3250/3280/
3300/3320/3340/3380/3450 mV) is linearly interpolated; voltages outside the table clamp to
0/100 %. *From the assignment.* *Impact:* SOC is a monotonic function of OCV; the table is a
const array.

**G5 — SOC persistence.** SOC is written to NVM every 60 s and on any parameter change, not
on every sample, to bound flash wear. *Not specified; 60 s is a compromise between accuracy
after reset and endurance.* *Impact:* a power loss can lose up to 60 s of SOC drift
(≈ 0.017 % of 100 Ah at 100 A).

## H. NVM (bonus B2)

**H1 — Slot geometry.** Two 512-byte HAL slots; each record contains magic `BMSN`, format
version 1, sequence, payload length, payload and CRC-16. *The assignment asks for versioning,
CRC, default fallback and wear levelling.* *Impact:* the newest valid sequence wins; a
corrupt slot is skipped; two invalid slots fall back to defaults.

**H2 — A/B is the wear-levelling strategy.** Alternating slots doubles endurance and
guarantees that a power loss during a write cannot destroy the previous valid record. *A true
log-structured region with erase counters is the production extension; two slots are the
right scope for two parameters.* *Impact:* endurance is 2 × the slot rating; the API
(`Nvm_Save`) is compatible with a future log backend.

**H3 — Synchronous NVM on the PC.** `Hal_NvmWrite` is a memory copy in the simulator. *A real
flash write can take tens of milliseconds; this is documented as a target integration task in
`docs/DESIGN.md` §3.3/§13.* *Impact:* the 100 ms task budget assumes a page-buffered HAL or a
move of the save to a slower task on target.

## I. Verification and tooling

**I1 — Unity is vendored and compiled with warnings suppressed.** *It is third-party MIT code
that is not modified; suppressing its warnings keeps `-Werror` meaningful for our code.*
*Impact:* our sources still build with the full warning set.

**I2 — Coverage metric.** "Branch coverage" is reported as gcov's "Taken at least once" (the
fraction of branch outcomes executed at least once). "Branches executed" is also reported but
is the weaker number. *This is the interpretation that actually demonstrates both outcomes of
each decision were tested.* *Impact:* both required modules exceed 85 % on the stricter
metric.

**I3 — Simulation semantics.** A scenario CSV row applies at its timestamp; a bus voltage of
0 means "tied to the pack"; the VCU close request is injected automatically every 100 ms with
a valid CRC and alive counter; the trace is sampled every 100 ms. *The assignment defines the
scenario idea but not the exact file schema; this schema is documented in
`sim/scenarios/*.csv` and `sim_main.c`.* *Impact:* scenarios are readable and reproducible;
the simulator injects the VCU command so the state machine can reach DRIVE/CHARGE.

**I4 — Plots are SVG.** The plotting tool is a small C program with fixed buffers and no
dependencies. *gnuplot/Python were unavailable.* *Impact:* the SVGs are checked in and can be
opened in any browser; regenerating them is part of the `simulate` target.

**I5 — Static analysis scope.** Cppcheck scans `src/` only, with `missingIncludeSystem` and
`unusedFunction` suppressed (justified in `docs/static_analysis.txt`). *Test code and
third-party Unity are not part of the deliverable's safety argument.* *Impact:* no findings in
the shipped firmware sources; test code is exercised by the compiler and the test run.

## J. Safety and scope

**J1 — No ISO 26262 claim.** The design follows a functional-safety mindset (safe state,
latched DTCs, hard thresholds, CRC, watchdog, bounded execution) but does not claim
compliance, ASIL decomposition or a full safety case. *The assignment asks for a mindset, not
a safety case.* *Impact:* a production programme would add a hazard analysis, FMEDA,
diagnostic coverage targets and independent review.

**J2 — Single CAN bus, no gateway.** The BMS transmits and receives on one classic CAN bus.
*From the assignment.* *Impact:* no bus redundancy, no node guarding beyond the alive
counter.

**J3 — Bootloader is design-only.** Bonus B2 explicitly says "design only"; the firmware
update half is documented but not implemented. Parameter storage is implemented. *From the
assignment.* *Impact:* the review can discuss the update design without untested boot code in
the tree.

**J4 — AI assistance is disclosed in the README.** The assignment requires disclosure of where
and how AI tools were used; `README.md` §7 does that. *From the assignment.* *Impact:* every
line remains explainable and modifiable during the review.
