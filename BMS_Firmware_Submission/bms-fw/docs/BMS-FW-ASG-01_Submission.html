1. The one-page answer

I built a complete, host-runnable BMS firmware in C11: a 1 ms tick with a 10 ms fast control cycle and a 100 ms main control cycle, a non-blocking AFE acquisition state machine with CRC and retries, table-driven passive balancing with hysteresis, adjacency and starvation control, a table-driven protection layer with 11 DTCs and derating, a table-driven CAN signal layer with CRC and alive counters, a UDS/ISO-TP diagnostic server, SOC estimation with OCV correction, and A/B NVM parameter storage. It has 88 unit tests, 100 % line coverage on balancing and 96 % branch coverage, 97 % line/91 % branch on protection, zero cppcheck findings, and two simulation scenarios with committed plots. The architecture is layered so that every safety-relevant decision is a pure function tested on the PC, and every hardware access is behind a HAL.

The four decisions that carry the design:

  1. Fixed cyclic executive, not an RTOS. Five periodic entries with hard, known periods. The scheduler gives deterministic order, bounded work per tick, an overrun counter, and a host build that behaves like the target. An RTOS would add footprint, priority-inversion analysis and non-reproducible timing for no functional gain.
  2. Every periodic activity is non-blocking and bounded. The AFE does one SPI transaction per 1 ms tick; CAN drains at most four frames per tick; NVM is the only potentially slow call and is isolated behind the HAL and documented.
  3. One source of truth per contract. FaultDef_t defines every protection behaviour; CanSignalDef_t defines every signal's bit position and scale; bms.dbc is the external contract; BalConfig_t defines every balancing threshold. Adding a fault, a signal or a threshold is a table edit, not a new branch.
  4. Safety is structural, not a claim. Safe state is the default, hard OV/UV/OC bypass the debounce, contactors are held for 1 s when opening is not urgent, all shared multi-field data is double-buffered, and every loop has a static bound. No malloc, no recursion, no variable-length arrays.

The honest limitations: no target hardware, so the timing numbers are conservative estimates; no MISRA add-on or clang-tidy in the environment; the bootloader half of B2 is design-only; NVM wear levelling would be log-structured in production.

4. Task 1 — architecture, scheduling, state machine, safety

4.1 Layering and the dependency rule

APPLICATION     scheduler, state machine, app orchestration, CAN/UDS glue
     │
SERVICES        balancing, protection, SOC, CAN signal/matrix, ISO-TP, UDS, NVM
     │
DRIVERS         AFE state machine, CAN queue/dispatch, NTC table
     │
HAL             time, SPI, contactors, voltages, current, temperature, CAN, NVM,
     │          critical section, watchdog
     ├── target: vendor HAL + real peripherals
     └── PC:     hal_sim.c + afe_sim.c

The rule is: arrows point down only. A service never includes a driver or application header. afe.c and can_driver.c are the only modules that call the HAL. That is what makes balancing, protection, SOC, the signal layer and UDS pure logic that runs on a PC with no mocking framework.

The HAL is an injected ops table (HalOps_t), not #ifdef and not weak symbols:

/* one explicit injection point; wrappers are NULL-safe */
typedef struct {
    uint32_t (*time_ms)(void);
    bool     (*spi_transfer)(const uint8_t *tx, uint16_t tx_len,
                             uint8_t *rx, uint16_t rx_len);
    void     (*set_contactor)(HalContactor_t which, bool closed);
    uint16_t (*pack_voltage_mv)(void);
    uint16_t (*bus_voltage_mv)(void);
    int32_t  (*pack_current_ma)(void);
    /* ... CAN, NVM, critical section, watchdog ... */
} HalOps_t;

Why not #ifdef? It makes it hard to build the target and the simulator from one tree and it hides which calls are hardware access. Why not weak symbols? Toolchain-specific and easy to link the wrong implementation silently. Why not a full RTOS HAL? The assignment does not need threads.

4.2 Scheduling

Chosen: a fixed cyclic executive. A 1 ms tick runs a table of five entries in registration order. The 1 ms entry is the scheduler quantum: it advances the AFE state machine by one bounded SPI transaction, drains CAN and kicks the watchdog. The control cycles required by the brief are the 10 ms fast task (current, over-current, protection, state machine) and the 100 ms main task (AFE cycle, balancing, CAN Tx). The order is the priority order.

Order Task Period Work Est. WCET Load
1 tick 1 ms advance the AFE state machine by one SPI transaction; apply a new balancing mask when a snapshot is published; drain ≤4 CAN Tx; dispatch ≤8 CAN Rx; kick watchdog 80 µs 8.0 %
2 fast 10 ms sample current; over-current; VCU monitor; protection/DTC; state machine/contactors; SOC; ISO-TP/UDS; publish snapshot 40 µs 0.40 %
3 main 100 ms force balancing off, start the AFE conversion, send 0x350/0x351, persist when due 60 µs 0.06 %
4 cellstats 500 ms send 0x352 15 µs 0.003 %
5 slow 1000 ms send 0x353 (6 mux frames) + 0x354 60 µs 0.006 %
Total ≈ 8.5 %

The 8.0 % for the tick is a deliberate upper bound: it charges 80 µs to every millisecond. The AFE is only active for about 22 ms of each 100 ms cycle, so the steady-state average is closer to 1–2 %. The bound is used so the timing budget cannot be argued downward.

Worst-case 1 ms tick: all five entries due at once ≈ 255 µs, still below the 1 ms quantum. The 10 ms fast task therefore has at least 9.7 ms of slack in every period.

Overrun policy. If a task's deadline has passed when it is next considered, the scheduler runs it once, re-bases the deadline to now + period, and increments an overrun counter. It does not catch up. Catching up would turn one late task into a burst of late work and could cascade into a missed watchdog. A missed deadline becomes observable telemetry instead of a hidden latency spike.

Why not an RTOS? Five fixed periodic entries do not justify the footprint, the priority-inversion analysis, the per-task stacks or the loss of host reproducibility. Why not a bare super-loop with delays? Blocking delays destroy jitter and make WCET unbounded, which contradicts the requirement. Why not timer-ISR work? Long ISRs block everything and are not composable with SPI/CAN. The full comparison is in §14.

The NVM caveat. On the PC, Hal_NvmWrite is a memory copy. On target, a data-flash page erase + program can take tens of milliseconds. A synchronous call from the 100 ms main task would delay the 10 ms fast task by the same amount, which is not acceptable for the over-current path. The operation is isolated behind Hal_NvmWrite; the production implementation must be page-buffered/non-blocking, or the save must be deferred to STANDBY. The delivered PC HAL keeps the build and tests deterministic. This is the top item in §19.

Precharge timing. The four phases are evaluated every 10 ms:

  1. 20 ms settle: NEG on, PRE off, POS off.
  2. One cycle: PRE on.
  3. Wait for bus ≥ 95 % of pack, timeout 2 s.
  4. 20 ms overlap: POS on, then PRE off on entering DRIVE/CHARGE.

A 20 ms settle is an engineering choice: it debounces the voltage comparison and guarantees overlap when the positive contactor closes. A precharge timeout emits a one-cycle pulse that the application feeds to protection as FAULT_PRECHARGE; the fault latches and clears through the normal DTC path.

Fault opening policy. Two independent outputs:

  • contactor_open_request — open, but first give the VCU 1 s to reduce current.
  • contactor_open_immediate — open on the same cycle for over-current, hard OV (>3750 mV), hard UV (≤2300 mV) and precharge failure.

This satisfies "never open under high current if it can be avoided" without slowing the fast protection paths.

VCU timeout. A missing/invalid 0x200 for 300 ms moves the system to STANDBY and opens after 1 s. It is reported as DTC 0x000A09 but deliberately excluded from fault_active, so a lost VCU is a communication loss, not a latched hardware fault.

4.4 Data sharing and concurrency

The application is single-context cooperative. On target the only ISR work is the 1 ms tick (increments a volatile counter) and short peripheral glue. Rules:

  1. AFE double buffer. Two AfeSnapshot_t buffers plus a volatile active index. The producer fills the inactive buffer, then swaps the index inside a critical section. Consumers copy the active buffer under the same section. No SPI runs inside it.
  2. Short critical sections. Only the index swap and the snapshot copy — no CRC, no loops over 16 cells, no blocking.
  3. volatile only where required. The active index and the tick counter. Arrays touched only in main context are not volatile, so the optimizer is not defeated.
  4. CAN Rx is polled. CanDrv_Poll() drains the HAL queue in the 1 ms tick task and calls handlers in main context. Handlers update small records; they do not block.
  5. Tx queue. 8 entries, ≤4 sends per poll, drop-newest with a counter. A full mailbox never blocks the 100 ms task.
  6. Application snapshot. App_GetSnapshot() copies under a critical section so the simulator, CAN and diagnostics see a coherent set of state, voltages, limits and faults.

Why double buffer, not a mutex or seqlock? A mutex can block and needs an RTOS; a seqlock is elegant but harder to review and needs an atomic sequence; a plain volatile array tears between fields. Double buffering is allocation-free, gives a consistent 16-cell set from one conversion, and the critical section is a few dozen bytes. It is the simplest mechanism that is obviously correct.

4.5 Functional safety mindset

The safe state is: both contactors open, precharge open, CCL = DCL = 0, balancing mask = 0, latched DTC recorded. Prot_Update() computes it from a table; application code cannot bypass the table.

5. Task 2 — AFE driver

5.1 Contract

SPI frame: [ADDR|R/W] [LEN] [DATA…] [CRC8], bit 7 of the address is write, CRC-8 poly 0x07, init 0x00, no reflection, no final XOR. Read response: [DATA…][CRC8], CRC over the data bytes. Device ID register 0x00 returns 0x5A. Cell registers are 16-bit big-endian, 100 µV/LSB. A 2 ms conversion is started by writing 0x01 to ADC_CTRL.

6. Task 3 — passive balancing

6.1 Requirements, restated as gates

Balancing may bleed only when all of these hold. First match wins, and the reason is reported in Bal_GetStatus().inhibit:

Order Inhibit Condition
1 BAL_INHIBIT_MEAS_PAUSE AFE conversion window (application forces mask 0)
2 BAL_INHIBIT_MEAS_INVALID snapshot invalid / stale
3 BAL_INHIBIT_FAULT any protection fault active
4 BAL_INHIBIT_VCU_DISABLED VCU balancing-enable bit is 0
5 BAL_INHIBIT_TIMEOUT 8 h continuous-balancing warning set
6 BAL_INHIBIT_OVER_TEMP cell ≥ 50.0 °C or board ≥ 70.0 °C; latched until 5 °C below both
7 BAL_INHIBIT_DISCHARGE pack current < −2 A
— BAL_INHIBIT_NONE run selection

6.2 Selection algorithm

every 100 ms:
  if gate active: mask = 0, active_time = 0 (except measurement pause), report reason
  else:
    find vmin, vmax
    if vmax < 3400 mV: mask = 0                  # LFP top-of-charge gate
    else:
      candidates = cells where
          (was bleeding  AND vcell - vmin >= 5 mV)   # stop threshold
       or (not bleeding AND vcell - vmin > 15 mV)   # start threshold
      sort candidates: priority cell first if within 20 mV of vmax,
                       then by descending voltage, ties by index
      for each candidate:
          stop if 8 selected
          skip if adding it creates an adjacent pair
          remember the first skipped cell as next cycle's priority
      mask = selected
      accumulate active time; at 8 h: mask = 0, warning, inhibit

Why 15/5 mV hysteresis? A single threshold chatters when a cell sits near the boundary and the bleed current perturbs the measurement. 15 mV start / 5 mV stop gives a 10 mV dead band, so a cell that starts bleeding keeps bleeding until it is genuinely closer to the pack minimum.

Why max 8 cells? The board thermal limit and the adjacency rule both cap the theoretical maximum at 8 (16 cells, no two neighbours). The configuration is validated to 1…16.

How starvation is prevented. A naive loop always drops the same lowest-priority cell of an adjacent pair. The algorithm records the first cell rejected by the max-cell or adjacency rule and promotes it to the front of the next cycle's candidate list — but only if it is within 20 mV of Vmax. A genuinely much-higher cell still wins. This is deterministic, bounded and directly targets the cell that missed out; random or fixed odd/even schemes are neither.

Why an 8 h timeout? Continuous bleeding for days is a symptom (a cell that never converges, a measurement offset, a stuck switch). The timeout stops it, raises a warning and requires a charge cycle to clear. It is a warning, not a DTC, because it is not a pack hazard by itself.

Measurement-window pause. The application forces the mask to 0 before starting a conversion and restores the newly computed mask when a snapshot is published. This prevents the bleed current's IR drop from corrupting the cell voltage being measured. The cost is ≈ 22 ms of every 100 ms cycle, so the maximum duty is ≈ 78 %.

7. Task 4 — protection and DTCs

7.1 Table-driven design

FaultDef_t holds: DTC, set threshold, release threshold, debounce, latch, action mask, set/release condition functions, and an optional hard threshold. One generic object (active, pending, confirmed, release_ok, timer, ISO 14229 status) implements all 11.

Why? Eleven copied if blocks diverge over time, and the DTC status logic becomes untestable. The table makes thresholds, actions and release conditions data; one state machine executes them. Adding a fault is a table row plus a condition pair.

The current sensor is specified as ±300 A. The over-current thresholds are deliberately set below full scale — 200 A discharge and 100 A charge — so the comparator trips while the signal is still in its linear range and the contactor opens before the sensor saturates. The thresholds are configuration, not hard-coded to the sensor range.

7.3 Debounce semantics

set condition true  ──► timer += dt
                        timer >= debounce?
                            yes: active = true, latch if configured
set condition false ──► timer = 0        # a single bad sample cannot accumulate
active + release true ──► release_ok = true
release false         ──► release_ok = false
clear request + release_ok + latched ──► clear active/latch, record "since clear"
clear request while condition present ──► ignored

An accumulated timer is used instead of a timestamp because it is explicit about elapsed time, works with a variable step, is immune to clock wrap, and is trivial to test with synthetic time.

8.2 Signal layer

A descriptor is the single source of truth:

typedef struct {
    uint8_t  start_bit;
    uint8_t  length;
    CanSigType_t type;      /* unsigned / signed */
    int32_t  scale_num;
    int32_t  scale_den;
    int32_t  offset;
    int32_t  phys_min;
    int32_t  phys_max;
} CanSignalDef_t;

Packing:

  1. saturate the physical value to [phys_min, phys_max];
  2. subtract the offset, multiply by den, divide by num with round-to-nearest;
  3. clamp to the raw range for the bit length and signedness;
  4. write bits little-endian across byte boundaries into a cleared frame;
  5. compute the CRC last, over bytes 0–6.

Why a table? Hand-written shifts duplicate sign extension, offset and cross-byte logic for every signal, and those are the classic CAN bugs. The table is tested once and reused for every message. Why not a struct overlay? Alignment, packing, endianness and strict aliasing make it undefined behaviour; see the review in §10.

Vertical signals: PackVoltage 0.01 V/bit, PackCurrent 0.1 A/bit signed (positive = charge), SOC 0.5 %/bit, CCL/DCL 0.1 A/bit, temperatures 1 °C/bit with −40 offset.

8.3 VCU command supervision

The receiver rejects, separately counted:

  • wrong DLC;
  • wrong CRC;
  • an unchanged 4-bit alive counter;
  • an alive jump > 2 (mod 16).

Three consecutive invalid frames are treated as a timeout. A single lost frame does not trip it; a stuck or spoofed counter does. A timeout moves the state machine to STANDBY and opens after 1 s, and raises DTC 0x000A09.

8.5 ISO-TP multi-frame sequence

The BMS is the responder. For DID 0x0100 (32 bytes):

tester → BMS   0x7E0  SF  [02 22 01 00 ...]        request
BMS → tester   0x7E8  FF  [10 24 62 01 00 ...]     32-byte length, first 6 bytes
tester → BMS   0x7E8  FC  [30 00 00 ...]           continue, block size, STmin

BMS → tester   0x7E8  CF  [22 ...]                 ...

Block size and STmin are honoured on transmit; the sender waits for FC between blocks and aborts after the FC timeout. Only one reception and one transmission are active at a time, which is sufficient for a request/response server. No CAN-FD, no extended addressing.

10. Task 7 — code review

The full review is in CODE_REVIEW.md. It covers the three listings in the brief and reports 47 findings: 19 critical, 17 major, 10 minor, 1 nit.

The five root causes:

  1. No ISR/task ownership boundary. The supplied handler parses a 64-byte frame, calls log(), opens contactors, sets DTCs, writes SPI and sends CAN inside the SPI interrupt. The corrected design moves bytes only in the ISR and runs a state machine in the 1 ms task.
  2. No error path. Unchecked reads, ignored return values, no conversion timeout, no retry limit. The corrected AFE has a deadline, a retry counter and a latched comm fault.
  3. No safety policy in the algorithm. The supplied balancing function has no measurement-window, temperature, fault, VCU or discharge gate, and no max-cell or timeout limit. The corrected Bal_Run makes every gate explicit.
  4. The wire contract is duplicated by hand. The supplied CAN function writes millivolts and amps into signals scaled as 0.01 V and 0.1 A, omits the CRC, and puts the alive counter in the wrong byte. The corrected signal table derives layout and scale from one definition, and the DBC is the external check.
  5. Undefined behaviour. i <= 16, 1 << 16, a signed right shift, and a struct overlay on a byte buffer. The corrected code uses bounded loops, unsigned masks, explicit two's-complement conversion and bit-level packing.

The review verdict is changes required, with six acceptance criteria: no parsing in the ISR; no volatile array treated as atomic; every loop bounded and every blocking call timed; every signal decoded by a DBC-derived test; every fault tested for set/reset/release/clear; strict build + cppcheck + coverage. All six are met by the delivered tree.

12. Bonus B1 — SOC estimation

12.1 Algorithm

Runs every 10 ms:

I_corr = I_measured - I_offset
if I_corr > 0: I_eff = I_corr × η        # η = 0.990, charge only
else:         I_eff = I_corr

ΔQ_uAh = I_eff × Δt_ms / 3600           # 1 uAh = 3600 mA·ms
SOC    = clamp(SOC + ΔQ / (C × 1000) × 1000, 0, 1000)   # permille

Charge is accumulated in micro-amp-hours with a 64-bit remainder so a 10 ms step does not lose precision through repeated integer division. A second remainder keeps the SOC update exact.

Offset learning: while |I| < 0.5 A, average the current for 30 s and store the average as the offset (clamped to ±2 A). This removes a persistent sensor bias at rest.

OCV correction: after 1 h at rest (|I| < 0.5 A), convert the cell OCV through the supplied table (0/10/20/30/50/70/90/95/100 % → 2800/3200/3250/3280/3300/3320/3340/3380/3450 mV) with linear interpolation, and move SOC toward it. The weight is 5 % between 3.28 V and 3.34 V (the flat LFP region) and 25 % outside it. The correction is applied once per rest period; a 5 ‰ dead band prevents pointless updates.

12.2 Why this design

Option Why not
Coulomb counting only Drifts with offset and efficiency error; no absolute anchor
OCV only Unusable under load; LFP OCV is flat across most of the range
EKF Needs a cell model, tuning, matrix maths and floating point; not justified for one pack current sensor
Coulomb + offset + weighted OCV (chosen) Fixed point, bounded, uses the supplied table, and explicitly handles the flat region

Persistence: SOC is written to NVM every 60 s and on parameter changes, not on every sample, to bound flash wear. A power loss can lose up to 60 s of drift (≈0.017 % of 100 Ah at 100 A).

Limitation: the OCV correction assumes the pack is at rest and uses the minimum cell voltage supplied by the application; it does not model hysteresis or temperature dependence. Those are documented as the next refinements.

13. Bonus B2 — parameter storage and firmware update

13.1 Parameter storage (implemented)

Record layout per slot:

offset  size  field
0       4     magic 'BMSN' (0x424D534E)
4       2     format version (1)
6       4     sequence number
10      2     payload length
12      N     payload (NvmParams_t: bal_start, bal_stop, soc_permille, flags)
12+N    2     CRC-16 over the header + payload

Algorithm:

  1. Load both slots; validate magic, version, length ≤ 64 and CRC.
  2. Choose the valid slot with the highest sequence.
  3. If both are invalid/blank, return defaults and report "no valid slot".
  4. Save: write the older slot with sequence + 1, then verify by reading back.
  5. A power loss during a write leaves the other slot valid, so the previous parameters are never lost.

Why A/B and not a single record? A single record is destroyed by a power loss mid-write. Why not wear-levelled log? It is the right production answer for frequent writes, but two parameters do not justify it; the API is compatible with a future log backend. Endurance is 2× the slot rating.

13.2 Firmware update (design only, as permitted)

Bootloader flow over CAN using UDS:

0x10 02   enter programming session
0x27      security access (seed/key)
0x34      request download (address, size)
0x36      transfer data (blocks)
0x37      request transfer exit
0x31 01   check integrity (hash/signature)
0x31 01   activate new image

A/B image layout:

┌──────────────┬──────────────┬──────────────────────┐
│ Bootloader   │ Image A      │ Image B              │
│ (immutable)  │ + manifest   │ + manifest           │
└──────────────┴──────────────┴──────────────────────┘
manifest: version, length, SHA-256, ECDSA/RSA signature, confirmed flag

Recovery rules:

  • The bootloader always boots the last confirmed image.
  • A new image is confirmed only after the application passes its self-test and writes the confirm flag.
  • Power loss during download: the old image remains valid.
  • Power loss during confirmation: the bootloader falls back to the old image.
  • Signature failure: the image is never booted; the old image stays.

The application and bootloader share the CAN/ISO-TP/UDS transport, not the safety logic. This is a design, not shipped code — the assignment marks B2 design-only, and untested boot code would be worse than a clear design.

17. Likely questions and model answers

Q1. Why no RTOS? Five fixed periodic jobs with known WCET. A cooperative table gives deterministic order, bounded work per tick, an overrun counter and a host build that behaves like the target. An RTOS adds RAM/flash, per-task stacks, priority-inversion analysis and non-reproducible host timing without adding functionality. I would move to an RTOS if a driver needed to block, if there were many asynchronous priorities, or if a task had to preempt another.

Q2. What happens if a task overruns? It runs once, the deadline is re-based to now + period, and the overrun counter increments. No catch-up. That bounds the work in the next tick and turns a missed deadline into telemetry instead of a latency burst.

Q3. How do you know the 1 ms tick and the 10 ms fast task fit? The 1 ms tick is one bounded SPI step plus CAN drain: a 3–5 byte transfer at 1 MHz plus driver overhead is 30–50 µs, so 80 µs is a conservative bound (8 % if charged to every tick). The AFE is active only ~22 ms per 100 ms, so the average is closer to 1–2 %. The 10 ms fast task is ~40 µs (0.4 %). On target I would toggle a GPIO at task entry/exit and measure with a scope or DWT cycle counter; that is explicitly the next step because there is no hardware here.

Q4. Why one SPI transaction per tick instead of reading all cells at once? A single blocking burst would violate the "do not block while waiting for conversion" requirement and make the tick's WCET depend on the AFE. One transaction per tick gives a bounded step, a natural retry point, and a 22 ms scan that is still far inside the 100 ms control cycle.

Q5. Why double buffering instead of a mutex? No RTOS and no blocking. A mutex would block the producer or consumer and needs priority inheritance. Double buffering gives a coherent set with a critical section of a few dozen bytes, and no SPI runs inside it.

Q6. Why not a seqlock? It is correct, but it needs atomic sequence handling and careful retry logic. Double buffering is simpler to review and has a fixed, tiny critical section. For 16 cells the copy cost is irrelevant.

Q7. How do you prevent torn 16-bit reads? I do not rely on the width. The whole snapshot is copied under a critical section, so the consumer sees one complete conversion. Individual 16-bit reads being atomic on Cortex-M is not the argument.

Q8. Explain balancing in 30 seconds. Gate on valid measurement, no fault, VCU enable, temperature, not discharging. Require Vmax ≥ 3.4 V. A cell starts bleeding above 15 mV over the minimum and continues until 5 mV. Sort by voltage, cap at 8 cells, reject adjacent pairs, and give the first skipped cell priority next cycle if it is within 20 mV of the maximum. Stop after 8 h and require a charge cycle to clear.

Q9. Why voltage-based, not SOC-based? LFP OCV is flat from about 30 % to 90 % SOC, so mid-range voltage differences say little. At the top of charge the curve steepens and voltage is a usable proxy. The BOM has one pack current sensor, not per-cell current, so per-cell SOC would be a model guess. Voltage-based top-balancing is the standard choice for passive bleed.

Q10. How do you prevent two adjacent cells from bleeding? Adjacent(mask) = (mask & (mask << 1)) != 0. Candidates are added one at a time; a candidate that would create an adjacent pair is skipped and becomes the starvation priority.

Q11. What if nine cells qualify? The first eight non-adjacent cells are selected; the first rejected cell is remembered. With 16 cells and no adjacency the maximum is eight, so the limit and the adjacency rule agree.

Q12. How do you prevent starvation? Remember the first cell dropped by the max-cell or adjacency rule. Next cycle, if it is within 20 mV of Vmax, sort it first. A much higher cell still wins, so fairness never overrides a real divergence.

Q13. Why 15/5 mV? Enough hysteresis to stop chatter from bleed-current IR drop and measurement noise, small enough to converge in a reasonable time. It is calibratable in BalConfig_t and validated (5–50 mV start, stop < start).

Q14. Why an 8 h timeout? Continuous balancing for days indicates a cell that will not converge, a measurement offset, or a stuck switch. Stopping and warning is safer than continuing. A charge cycle is the natural proof that the pack has been cycled and the warning can clear.

Q15. How does the measurement window work? The application forces the mask to zero before starting an AFE conversion and applies the new mask only after a valid snapshot is published. That removes the bleed current's IR drop from the measurement. Cost: ≈22 ms per 100 ms, so ≈78 % maximum duty.

Q16. Walk me through the protection debounce. Each fault has a set condition, a release condition, a debounce, a latch flag and an action mask. While set, an accumulator grows by dt; when it reaches the debounce the fault becomes active and latches if configured. A single false sample resets the accumulator. Release is evaluated even while active; a latched fault clears only when release is true and a clear request arrives.

Q17. Why table-driven protection? Eleven copies of the same debounce/status logic diverge. The table makes thresholds, actions, release conditions and DTCs data; one state machine executes them. Adding a fault is a row plus a condition pair, and the status logic is tested once.

Q18. How do you avoid opening contactors under load? Non-urgent faults request an open but the state machine holds for 1 s so the VCU can reduce current. Over-current, hard OV (>3750 mV), hard UV (≤2300 mV) and precharge failure request an immediate open, independent of the debounce. That is the explicit exception in the requirement.

Q19. Why is VCU timeout not a FAULT? The assignment says "go to STANDBY, open after 1 s". A lost VCU is a communication loss, not a pack hazard. It is still a DTC and still opens the contactors after 1 s, but it does not latch the hardware fault state. That lets the system recover when the VCU returns.

Q20. Explain the DTC clear semantics. A clear request alone does nothing if the release condition is false. When release is true, the active/latch state clears and the status records "test not completed since clear" / "failed since clear" as appropriate. The DTC remains visible to 0x19 until it is retested, so the tester can see the history rather than the record vanishing.

Q21. How are CCL and DCL derived? Take the minimum of the temperature derating and the voltage derating, then ramp at 100 mA/ms. Charge: 0 below 0 °C, 50 A at 5 °C, 100 A to 45 °C, 0 at 55 °C. Discharge: 0 below −20 °C, 100 A at 0 °C, 200 A to 45 °C, 0 at 60 °C. Voltage tapers: 100→0 A from 3550→3650 mV charge, 0→200 A from 2500→3000 mV discharge. Both start at 0 at boot.

Q22. Why CRC-8 SAE J1850 and a 4-bit alive counter? CRC-8 catches bus/EMC corruption on safety-relevant frames; the alive counter catches a stuck or replayed transmitter. Four bits fit the byte layout and wrap 15→0; the receiver rejects repeats and jumps >2. 0x352–0x354 are low-rate informative frames and deliberately carry no CRC, as specified.

Q23. How does UDS 0x0100 fit in 8 bytes? It does not, so ISO-TP multi-frame is used: First Frame with the 32-byte length, tester Flow Control, then Consecutive Frames. Block size and STmin are honoured; a missing FC aborts after the timeout. The BMS is the responder; the tester sends the FC.

Q24. Why does SOC correct slowly in the flat region? Because a few millivolts there correspond to tens of percent SOC. A 25 % correction on a 3.30 V reading could jump SOC by 20 points for a tiny measurement error. The 5 % weight between 3.28 V and 3.34 V makes the correction slow and stable; on the steep edges 25 % is safe because the voltage-to-SOC slope is high.

Q25. How is NVM power-loss safe? Two slots, each with magic, version, sequence, length and CRC-16. Save writes the older slot with sequence+1. A power loss mid-write leaves the other slot valid. On boot, the newest valid record wins; if both are corrupt, defaults are used and reported.

Q26. What does the bootloader do on a bad signature or a power loss? It never boots an unconfirmed or invalid image. The last confirmed image stays valid. A new image is confirmed only after the application self-test writes the confirm flag. Power loss during download or confirmation leaves the old image bootable.

Q27. What is the biggest risk in this design? The NVM write latency on target, because it is the one potentially unbounded operation inside a periodic task. It is isolated behind the HAL, quantified, and has a clear fix (non-blocking page buffer or move to the 1 s task). The second is the lack of target timing measurements; the 8.5 % load is an estimate, and the next step is GPIO/WCET measurement.

Q28. What would you do with another week? Measure WCET on target, make NVM non-blocking, add cell open-wire localisation, add a GitHub Actions CI file, run a MISRA check with a deviation list, add temperature-dependent OCV/hysteresis to SOC, and implement the bootloader if hardware were available.

Q29. How was AI used, and how do you know the code is correct? It drafted skeleton and implementation material, which I reviewed line by line, compiled under -Werror, exercised with 88 tests, two simulations and cppcheck. Defects found during that review were fixed in code and tests. The design rationale is written down so I can defend or change every decision. No AI runs at runtime and no generated code is linked unreviewed.

Q30. If I change the cell count to 12, what breaks? AFE_CELL_COUNT, BAL_CELL_COUNT, PROT_CELL_COUNT, the CAN mux count and the DBC need to change together; the code is table/count driven, so the algorithms are unchanged. The tests use the count constant. I would add a compile-time assertion that the three counts agree and that the mux count covers ceil(N/3). That is the honest answer: the design is count-driven but the constants are not yet centralised in one header.

18. The three-day plan

Day 1 — architecture and acquisition

  • Decide scheduling, layering, HAL injection, state machine and fault policy.
  • Implement common (CRC, saturation), HAL simulator, AFE register model and driver.
  • Bring up the scheduler and the state machine with synthetic inputs.

  • Protection: FaultDef_t, debounce/DTC object, derating, ramp, hard thresholds.
  • CAN signal layer, CAN matrix, DBC, VCU monitor, Tx queue.
  • ISO-TP and UDS subset; unit tests for every service.
  • Start coverage and close the gaps.

Day 3 — evidence and documentation

  • Simulation scenarios, trace schema, SVG plotter, run and inspect the traces.
  • Coverage to target, cppcheck, strict build, stack measurement.
  • README, DESIGN, ASSUMPTIONS, CODE_REVIEW, coverage/static-analysis reports.
  • Final pass: re-read every file, check requirement traceability, verify one-command build.

The plan deliberately front-loads the architecture because a bad layering decision on day 3 cannot be fixed in the time left. Bonuses were implemented after the mandatory paths were green, not before.
